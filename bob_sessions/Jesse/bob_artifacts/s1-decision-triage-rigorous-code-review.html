1 — Semantic Classification & Precedence (triagePrompt)

P1 · Major
hasExplicitPrecedence suppresses rule_conflict classification but does not suppress the "action" tier — a prompt with "prefer X over Y" + "conflict" still scores 0.92 and routes to Granite as rule_conflict
S1TriageAdapter.cpp lines 80–101
Root cause

hasUnresolvedConflictPhrase (line 92) is correctly gated: 

lowerPrompt.find("conflict") != npos && !hasExplicitPrecedence

This means "conflict" alone, when paired with explicit precedence, does not trigger the rule_conflict branch — good. However, hasContradictoryInvariants (line 88) is evaluated entirely independently of hasExplicitPrecedence: 

const bool hasContradictoryInvariants =
    (lowerPrompt.find("stateless") != npos &&
     (lowerPrompt.find("session") != npos || lowerPrompt.find("sticky") != npos));

The branch on line 97 is: 

if (hasContradictoryInvariants || hasUnresolvedConflictPhrase) { … rule_conflict … }

A prompt such as "prefer stateless over sticky session storage" sets hasExplicitPrecedence = true (via "prefer … over") and hasContradictoryInvariants = true (stateless + session). The gate on hasUnresolvedConflictPhrase correctly suppresses the "conflict" keyword path, but hasContradictoryInvariants is still true, so the rule_conflict branch fires at 0.92 regardless. The explicit-precedence signal is ignored for this class of prompt.

Impact

Every well-formed architectural preference statement involving stateless/session or stateless/sticky terminology is mis-classified as a high-score rule conflict and sent to the Granite discovery flow unnecessarily, producing spurious clarification dialogs.

Fix
const bool hasContradictoryInvariants =
    !hasExplicitPrecedence &&          // ← suppress when precedence is resolved
    (lowerPrompt.find("stateless") != npos &&
     (lowerPrompt.find("session") != npos || lowerPrompt.find("sticky") != npos));
P1 · Major
fastPathClear is set to false for Empty and WhitespaceOnly inputs — HostController.analyzePrompt() has a separate pre-triage guard but other callers may not, creating a bypass gap
S1TriageAdapter.cpp lines 57, 69; HostController.cpp line 679
Root cause

For Empty and WhitespaceOnly inputs the adapter correctly sets fastPathClear = false (lines 57, 69), which means the caller will not take the fast path and may attempt to proceed to Granite discovery. The intent behind setting fastPathClear = false here is ambiguous: it appears designed to prevent a silent no-op, but without a paired isAmbiguous = false + explicit caller guard, an unsuspecting new caller who only checks fastPathClear would read it as "needs more processing" and attempt to construct a GraniteOptionDiscoveryRequest with an empty prompt string.

HostController::analyzePrompt() (line 679) performs its own text.trimmed().isEmpty() pre-check before calling triagePrompt, which shields the production path. However:

  • There is no enforcement that every future caller replicates this guard.
  • The S1TriageDecision type provides no ergonomic way to distinguish "invalid input, stop here" from "valid but unambiguous, fast-path clear" from the caller side — both use the bool fastPathClear field but for orthogonal reasons.
Fix — decouple the two concerns at the type level

The cleanest fix is to make inputValidity != Valid act as its own stop signal in every consumer. Either add a helper to the decision struct: 

[[nodiscard]] bool isExecutable() const noexcept {
    return inputValidity == InputValidity::Valid;
}

Or, simpler: set fastPathClear = true for invalid inputs. The "fast path" label means "no Granite invocation needed" — which is equally true for empty and whitespace-only prompts. Setting it false for invalid input is a semantic inversion that requires callers to apply a separate validity check first. Callers should not need to know two orthogonal predicates to safely dispatch.

P2 · Minor
Token " or " triggers the "action" ambiguity tier — false positive on common English conjunctions ("you or your team", "now or later")
S1TriageAdapter.cpp line 115

The action-tier check includes lowerPrompt.find(" or ") != npos. Any prompt containing a natural-language disjunction in a non-ambiguous context — "let me know if you or your team need anything", "refactor now or later" — will be classified as ambiguous at score 0.78 and routed to Granite. The token-level match has no surrounding context: it fires on every occurrence.

Recommended fix

Require the "or" to appear adjacent to technical or instructional tokens (e.g., require at least one adjacent technical keyword from a small set), or elevate this pattern's threshold requirement — e.g., only trigger when " or " appears and one of the other action-tier keywords also matches, making it a conjunction not a singleton trigger: 

const bool hasActionAmbiguity =
    lowerPrompt.find("timeout")  != npos ||
    lowerPrompt.find("refactor") != npos ||
    lowerPrompt.find("optimize") != npos ||
    lowerPrompt.find("handle")   != npos ||
    // " or " only counts when paired with an instructional context:
    (lowerPrompt.find(" or ") != npos &&
     (lowerPrompt.find("should") != npos || lowerPrompt.find("instead") != npos ||
      lowerPrompt.find("approach") != npos || lowerPrompt.find("strategy") != npos));
P2 · Minor
Hardcoded ambiguityScore constants (0.92, 0.88, 0.78, 0.22) and the clear-path threshold (0.70) are magic literals with no named constant or contract reference
S1TriageAdapter.cpp lines 99, 108, 117, 122, 129

The threshold on line 129 — decision.ambiguityScore < 0.70 — determines whether the entire Granite invocation is bypassed. The four score values (0.92, 0.88, 0.78, 0.22) are the only outputs the classification logic ever produces. static constexpr double kAmbiguityScoreAction        = 0.78;
static constexpr double kAmbiguityScoreClear         = 0.22;

2 — Probability Integrity & Contract C05 (Zero-Preselection)

P1 · Major
C05 Violation: evaluateSnapshot() assigns winningAlternativeId = group.alternatives[0].id when modelInferenceExecuted is true — first-option bias with a uniform distribution
S1TriageAdapter.cpp lines 194–204
Root cause
if (response.modelInferenceExecuted) {
    score.isScored = true;
    score.ambiguityScore = 0.82;     // ← hardcoded
    score.noulCertainty = true;
    if (n > 0) {
        const double uniform = 1.0 / static_cast(n);
        for (const auto& alt : group.alternatives) {
            score.probabilities.push_back({alt.id, uniform});
        }
        score.winningAlternativeId = group.alternatives[0].id;  // ← C05 violation
    }
}

When localModelLoaded_ = true, the adapter claims executionStatus = ExecutedModel, sets isScored = true and noulCertainty = true — all signals that a real inference result is present — but then assigns a uniform distribution (equal probability to every alternative) and picks the first alternative as winningAlternativeId. This is internally contradictory:

  • A uniform distribution means no ranking signal exists; there is no winner by definition.
  • Setting winningAlternativeId = alternatives[0] biases QML rendering (the HostController reads ap.probability to assign display weight) toward whichever alternative the model response happened to list first — a pure ordering artefact.
  • The hardcoded ambiguityScore = 0.82 is a fabricated certainty assertion; no inference was actually performed.
Contract C05 requirement

Contract C05 (Zero-Preselection) requires that when no real ranked score is produced, winningAlternativeId must be std::nullopt and probability values must be uniform (or absent) with isScored = false.

Fix

The localModelLoaded_ = true path is currently a stub that does not perform real inference. It must either be wired to an actual model call, or it must be treated identically to the unloaded path until real inference is implemented: 

// While Julia-local inference is not yet implemented:
if (localModelLoaded_) {
    response.executedEngine = ScorerEngine::JuliaLocal;
    response.executionStatus = ExecutionStatus::DegradedUnranked;  // honest
    response.modelInferenceExecuted = false;                        // honest
    // fall through to unscored uniform distribution below
}
// …
score.isScored = false;
score.ambiguityScore = 0.50;
score.noulCertainty = false;
score.winningAlternativeId = std::nullopt;
const double uniform = 1.0 / static_cast(n);
for (const auto& alt : group.alternatives)
    score.probabilities.push_back({alt.id, uniform});

Alternatively, if this branch genuinely invokes a model and returns a real ranked distribution, populate probabilities from the model output and derive winningAlternativeId from the highest-probability entry — not from alternatives[0].

P2 · Minor
evaluateSnapshot() unconditionally overwrites response.success = true on line 222 — can mask a prior false set on the cloud-available path
S1TriageAdapter.cpp line 222
Root cause

The cloud unavailable path (lines 156–164) returns early with response.success = false — correct. But the cloudAvailable_ = true branch (lines 166–170) sets response.success = true inline, and then the local-model branch (lines 179) also sets it inline. Both those branches are followed by the group-scoring loop, and then line 222: 

response.success = true;  // ← unconditional

This is harmless today because every non-early-return path already sets success = true before reaching line 222. However, if a future branch sets success = false but falls through the group-scoring loop (e.g., a partial-failure with degraded results), this line silently resets the flag to true.

Fix

Remove line 222; every reachable path that should succeed already sets response.success = true explicitly in its own branch.

When modelInferenceExecuted = false (both the cloud-unranked and local-not-loaded paths), the adapter correctly sets isScored = false, noulCertainty = false, winningAlternativeId = std::nullopt, and assigns a true uniform distribution. 3 — 3-Tier Engine Taxonomy, Mock Injection & Latency

P2 · Minor
triagePrompt() mock path overwrites decision.engine unconditionally — mock handler cannot return a result attributed to a different engine (e.g. JevCloud) without having it silently corrected
S1TriageAdapter.cpp lines 43–47; hpp line 83
Root cause
auto decision = mockTriageHandler_(prompt, engine_);
const auto endTime = std::chrono::steady_clock::now();
decision.latencyMs = …;
decision.engine = engine_;    // ← unconditional overwrite

The mock handler receives engine_ as a parameter and may construct a S1TriageDecision with an engine field that reflects what it simulates (e.g. a cloud engine). Line 46 overwrites that field with the adapter's configured engine, making it impossible to test scenarios where the mock simulates a different engine tier than the one currently configured — a useful test case when validating cross-engine fallback logic.

Note: evaluateSnapshot() performs the analogous overwrite on line 145–146 (resp.engine = engine_; resp.executedEngine = engine_;), with the additional concern that it also forces executedEngine = engine_ even though a mock might legitimately want to return executedEngine = std::nullopt to simulate a degraded path.

Fix

Only overwrite latencyMs (which the mock cannot know) and leave engine and executedEngine as returned by the mock handler. Document this as the contract: 

auto decision = mockTriageHandler_(prompt, engine_);
decision.latencyMs = std::chrono::duration(
    std::chrono::steady_clock::now() - startTime).count();
// engine is mock's responsibility to set correctly
return decision;
P2 · Minor
configuredEngine() and engine() are identical — redundant accessor pair with no type distinction between "configured" and "currently executing" engine
S1TriageAdapter.hpp lines 82–83

The header exposes two methods that return the exact same value from the exact same field: 

[[nodiscard]] ScorerEngine engine() const noexcept         { return engine_; }
[[nodiscard]] ScorerEngine configuredEngine() const noexcept { return engine_; }

The intent is presumably to signal the semantic distinction between the user-configured preference (which engine is desired) and the runtime execution (which engine actually ran). However, both return the same engine_ member, so the distinction exists only in naming, not in data. The actual "executed engine" is captured in SnapshotEvaluationResponse::executedEngine (an optional<ScorerEngine>) — which is correct. On the adapter object itself, a single configuredEngine() is sufficient; engine() is a confusing alias that implies something observable at runtime.

Recommendation

Deprecate or remove engine(); keep only configuredEngine(), which has the clearer semantic. Document that "executed engine" is readable only from the per-call response structs.

Clean
Mock handler injection is exception-safe and does not corrupt state on throw
S1TriageAdapter.cpp lines 42–48, 141–150

Unlike the GraniteAdapter mock path (which had a state-stuck-at-Busy bug), the S1TriageAdapter mock paths carry no mutable adapter state between start and end. triagePrompt does not set a "busy" flag before calling the mock, so if the mock throws, the adapter remains in its prior valid state. evaluateSnapshot similarly constructs a local response object and returns it; no persistent state is mutated in the hot path.

Clean
steady_clock latency measurement correctly placed — start before mock/engine dispatch, end after; no double-timing artefacts
S1TriageAdapter.cpp lines 40, 44–45, 60–61, 72–73, 131–132, 139, 143–144, 162–163, 223–224

startTime is captured as the first statement in both triagePrompt and evaluateSnapshot. All return paths — early-exit for empty/whitespace, mock path, every engine branch — capture endTime immediately before assigning latencyMs/totalLatencyMs. There are no paths that return without setting the latency field. steady_clock (monotonic) is the correct clock for latency measurement.

Clean
availability() correctly models the 3-tier taxonomy — configuredEngine drives the check, not executedEngine
S1TriageAdapter.cpp lines 30–37; hpp lines 19–23

availability() returns a SemanticAvailability based on both the configured engine preference (engine_) and its runtime readiness flag (cloudAvailable_ or localModelLoaded_). The three-value enum (FullRankedCloud, FullRankedLocal, DegradedUnranked) correctly represents the distinct tiers: cloud-scored, local-scored, and no-score-available. The return value is independent of executedEngine on the response structs, which is the correct separation of concerns.
