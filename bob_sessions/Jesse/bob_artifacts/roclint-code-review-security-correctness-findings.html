1 — src/bridge/GraniteAdapter.cpp

P0 · Critical
skipValue(): object/array scanner increments pos_ after parseString() has already advanced it — causes double-advance and potential OOB read
Lines 120–128 (object branch), 135–143 (array branch)
Root cause

Inside the depth-tracking loops for {} and [], when the current character is ", the code calls parseString(dummy) which internally advances pos_ past the entire quoted token (including its closing "). But then ++pos_ on line 127/142 runs unconditionally after the string call, advancing one extra character. This means one byte following the closing quote is silently skipped. If the closing " is the last character before } or is adjacent to another structural character, pos_ can exceed src_.size() — and the depth counter may never reach zero, turning the loop into an infinite walk to EOF, or mis-parsing the depth so the caller sees depth == 0 at the wrong offset.

Affected input example
{"key": "val"}  →  after parseString("val"), pos_ is at '"'→'}' boundary;
++pos_ then skips '}', depth never decrements, loop exhausts input,
returns depth==1 (failure) or overshoots into adjacent data.
Fix

Use continue after parseString to skip the unconditional ++pos_:

if (src_[pos_] == '"') {
    std::string dummy;
    parseString(dummy);
    continue;          // ← already advanced; do NOT ++pos_ again
}
if (src_[pos_] == '{') ++depth;
else if (src_[pos_] == '}') --depth;
++pos_;

This is already the correct pattern for the array branch too (lines 135–143, same fix required).

P1 · Major
parseString(): backslash at EOF silently swallowed — truncated escape not detected
Lines 80–81
Root cause

The escape guard is if (c == '\\' && pos_ < src_.size()). When a backslash is the very last byte of the buffer, the condition is false, so the else branch fires and the lone \ is appended verbatim to out — producing a corrupt string that the caller treats as a valid parsed value. The outer while then loops back, immediately sees pos_ >= src_.size(), and returns false, but by then a partial value has already been accumulated. Callers such as parseDiscoveryResponse use the bool return only on specific keys; for status (line 202) and error (line 204) the return value is discarded entirely, so a truncated escape in the "error" field silently sets response.errorMessage to a garbled string.

Fix
if (c == '\\') {
    if (pos_ >= src_.size()) return false;  // ← truncated escape = parse failure
    char esc = src_[pos_++];
    // … switch …
}
P1 · Major
parseDiscoveryResponse(): infinite loop on malformed inner objects — inner while (peek() != '}' && hasMore()) never terminates when } is absent
Lines 212, 229, 236
Root cause

The parseString/skipValue calls inside the inner while loops each advance pos_ until they either succeed or hit EOF and return false. When they return false (e.g., a key string with no closing quote), pos_ is left at src_.size(), hasMore() becomes false, but peek() returns '\0' — which is not '}'. So the loop condition peek() != '}' && hasMore() evaluates to true && false == false and exits correctly only when hasMore() becomes false.

However, if parseString or expect(':') return false without advancing pos_ (e.g. an unexpected byte type), pos_ stays still: the inner loop then spins forever calling the same failing operation on the same byte. Concretely, if the gKey parse succeeds but expect(':') (line 215) returns false because : is absent, pos_ is left just after the key string; the subsequent if/else if chain for gKey matches nothing and calls skipValue() — which might also not advance (empty input). The next iteration's parseString(gKey) succeeds again on the same character, creating an infinite loop.

Fix

Propagate failure returns: replace silent ignoring of parseString/expect results in inner loops with explicit early-exit on parse failure, e.g.:

if (!parser.parseString(gKey)) {
    response.success = false;
    response.errorMessage = "Malformed JSON in choice_group key";
    return response;
}
if (!parser.expect(':')) {
    response.success = false;
    response.errorMessage = "Malformed JSON: missing ':' in choice_group";
    return response;
}

Apply the same pattern to the alternatives inner object loop (lines 238–239).

2 — src/storage/Database.cpp

P1 · Major
PRAGMA foreign_keys / journal_mode not re-applied on reopen or after move-assign — SQLite connection settings are per-connection, not per-file
initializeSchema() lines 112–117; open() line 43; operator= line 119
Root cause

Both PRAGMAs are set only inside initializeSchema(). open() does not call initializeSchema(), so any caller that reopens the database via open(path) directly — or receives a database via move-assignment — gets a raw SQLite connection with foreign-key enforcement disabled (the SQLite default) and in rollback journal mode. Foreign-key cascade deletes on the prompt_revisions → sessions relationship would silently fail to cascade, leaving orphaned rows.

Fix (option A — document the invariant)

Add a [[nodiscard]] note to open() in the header stating that callers must call initializeSchema() or applyConnectionPragmas() after every open().

Fix (option B — enforce at the connection layer)
// In open(), after rc == SQLITE_OK check:
sqlite3_exec(db_, "PRAGMA foreign_keys = ON;", nullptr, nullptr, nullptr);
sqlite3_exec(db_, "PRAGMA journal_mode = WAL;", nullptr, nullptr, nullptr);

Option B is safer; the overhead of two PRAGMAs on open is negligible.

P2 · Minor
open() error path: errorMessage string is built from sqlite3_errmsg() before close() is called — close() invalidates the handle used by errmsg()
Lines 59–69

The current order is: (1) build errorMessage from sqlite3_errmsg(db_) → (2) close() → (3) throw. This is actually correct because the string is copied into errorMessage before close() destroys the handle. However, the logic path that falls into else { errorMessage += "Unknown error…" } (line 65–67) is misleading: sqlite3_open_v2 always writes a valid (potentially null) handle even on failure — the SQLite docs state the handle is valid and must be closed even when the return code is not SQLITE_OK. So the isOpen() check on line 60 will almost always be true, making the else branch dead code.

Fix

Drop the isOpen() guard; always call sqlite3_errmsg(db_) (which handles a partially-opened handle), build the string, then close:

if (rc != SQLITE_OK) {
    const std::string msg = db_ ? sqlite3_errmsg(db_) : "unknown error";
    close();   // safe; close() checks for nullptr
    throw std::runtime_error("Failed to open database: " + msg);
}
P2 · Minor
execute(): errMsg path calls sqlite3_free(errMsg) but the else-branch uses sqlite3_errmsg(db_) without freeing — minor double-path inconsistency, not a leak (errmsg is static buffer), but misleading
Lines 100–108

sqlite3_exec writes to errMsg on failure; that memory must be freed with sqlite3_free. The current code does this correctly on the if (errMsg) branch (line 103–104). The else branch (line 106) calls sqlite3_errmsg(db_) — this returns a pointer into SQLite's internal static buffer, which must not be freed. Both are handled correctly. However, the throw on line 108 is inside the if (rc != SQLITE_OK) block but incorrectly indented to look like it's outside the if (errMsg) sub-block (it is de-indented relative to the surrounding braces). This is purely a readability hazard; the logic is actually correct because sqlite3_free(nullptr) is a no-op if errMsg were somehow null.

Recommendation

Consolidate to a single pattern that always calls sqlite3_free (which is a no-op on nullptr) for clarity:

const int rc = sqlite3_exec(db_, sql.c_str(), nullptr, nullptr, &errMsg);
if (rc != SQLITE_OK) {
    std::string error = "SQLite execution error: ";
    error += errMsg ? errMsg : sqlite3_errmsg(db_);
    sqlite3_free(errMsg);
    throw std::runtime_error(error);
}

sqlite3_close_v2 lifecycle and move semantics — correct
Lines 33–37, 74–81, 119–128

sqlite3_close_v2 is always called through close() which null-checks first and nulls the pointer after. The move constructor and move-assignment both null out the source handle. Copy constructor and copy-assignment are deleted. No handle leaks on any exit path of open() (the failed path calls close() before throwing). Exception safety is upheld: destructor is noexcept and calls close().

P2 · Minor
analyzePrompt(): std::min() on potentially npos — undefined behaviour when promptStr contains no space
Lines 741–745
Root cause
const std::size_t end = std::min(promptStr.size(), promptStr.find(' '));

When promptStr.find(' ') returns std::string::npos (0xFFFF…FFFF), std::min correctly picks promptStr.size(), which is fine. However, the guard on line 744: 

(end != std::string::npos && end > 0) ? end : promptStr.size()

If find(' ') returns npos, the std::min already resolved end to promptStr.size(), which can never equal npos (unless the string is astronomically large). So the condition is effectively always-true here — but if promptStr.size() happened to equal npos, the extra guard would misfire. More importantly, the expression end != std::string::npos signals the author intended to handle the npos case, but the std::min above already consumed it, making the conditional a logical dead-end that misleads future readers.

Fix — replace with a single clear expression
const std::size_t spacePos = promptStr.find(' ');
const std::size_t end = (spacePos != std::string::npos) ? spacePos : promptStr.size();
for (auto& alt : group.alternatives) {
    alt.evidence.push_back(core::analysis::SourceSpan{0, end});
}
